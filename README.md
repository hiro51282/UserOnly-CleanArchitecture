# UserNameだけで学ぶ Clean Architecture 実験プロジェクト

## 目的

ユーザー名という最小ドメインを題材に、

* Clean Architecture
* DI（Dependency Injection）
* Command / UseCase設計
* Repositoryパターン
* トランザクション境界
* 一意制約の責任分離

を段階的に理解・実装・検証する。

機能を増やすことが目的ではない。
設計の密度を上げることが目的である。

---

# Clean Architecture 最小構成

## 本当に必要な層は4つだけ

```
① UI層
② アプリケーション層（UseCase / Command）
③ ドメイン層
④ インフラ層
```

以上。本質はこれだけ。

---

## 各層の役割

### ① UI層

* 入力を受け取る
* 結果を表示する
* トランザクションを開始する（フレームワークが担当することが多い）

例：

* CLI
* Controller
* React

---

### ② アプリケーション層（UseCase / Command）

業務操作の単位。

* 処理の流れを書く
* トランザクション境界になる
* ドメインを呼び出す
* Repositoryを呼び出す

例：

```
createUser
deleteUser
```

トランザクション境界は UseCase 単位。

---

### ③ ドメイン層

ビジネスルールのみを持つ。

* User
* UserName
* 重複は禁止（概念的ルール）

DBもUIも知らない。

---

### ④ インフラ層

技術的実装。

* MySQL実装
* InMemory実装
* HTTP
* File

整合性の物理保証（例：一意制約）はここ。

---

# 用語マッピング

| 用語                    | 属する層         |
| --------------------- | ------------ |
| Command               | アプリケーション層    |
| UseCase               | アプリケーション層    |
| DI                    | 層をつなぐ仕組み     |
| Repository(interface) | ドメイン寄りの境界    |
| Repository実装          | インフラ層        |
| トランザクション              | アプリケーション層で管理 |
| 一意制約(DB)              | インフラ層        |
| ValueObject           | ドメイン層        |
| Entity                | ドメイン層        |
| DomainService         | ドメイン層        |
| CompositionRoot       | UI層の近く       |

増えて見えるが、すべて4層に収まる。

---

# 依存方向

```
[ UI ]
   ↓
[ Application (UseCase / Command) ]
   ↓
[ Domain ]
   ↑
[ Infrastructure ]
```

依存は必ず内側へ向かう。

---

# なぜ混乱するのか

層が増えているのではない。

増えているのはパターンである。

* Commandパターン
* DI
* Repositoryパターン
* ValueObject
* DomainService

すべて4層の内部での話。

---

# 超圧縮版構造

```
UI → UseCase → Domain
          ↓
      Infrastructure
```

これが最小骨格。

---

# 重要な原則

トランザクション境界：

```
UseCase単位
```

一意制約の最終保証：

```
Infrastructure（DB）
```

ドメインの責務：

```
ビジネスの意味を定義すること
```

# 開発ステップとコミット方針

小刻みにコミットする。
履歴で設計の変化を追えるようにする。

---

## Step 1: Domainの最小実装

### 目的

User と UserName を作り、ビジネス概念を分離する。

### 設計意図

* UserNameをValueObjectにする
* プリミティブ汚染を避ける
* ドメインは技術を知らない

### トレードオフ

* 過剰設計に見える
* 小規模では恩恵が見えにくい

コミット例:

```
step1: add User and UserName domain model
```

---

## Step 2: Repository抽象を追加

### 目的

永続化を抽象化し依存方向を固定する。

### 設計意図

* interfaceをドメイン側に置く
* 実装詳細を隠蔽する

### トレードオフ

* 実装がまだ存在しないため抽象が浮く

コミット例:

```
step2: add UserRepository interface
```

---

## Step 3: InMemory実装

### 目的

具体実装を追加しDI可能な構造にする。

### 設計意図

* インフラ層を明確に分離
* 差し替え可能性を担保

### トレードオフ

* 並行性保証はない

コミット例:

```
step3: add InMemoryUserRepository
```

---

## Step 4: CreateUserCommand実装

### 目的

ユースケース単位の操作を定義する。

### 設計意図

* トランザクション境界はUseCase単位
* 重複チェックの位置を明確化

### トレードオフ

* アリスアリス問題は未解決

コミット例:

```
step4: add CreateUserCommand
```

---

## Step 5: テスト追加

### 目的

構造がテストしやすいことを確認する。

### 設計意図

* DIの効果を確認
* インメモリ実装をそのまま利用

### トレードオフ

* 並行性テストは別途必要

コミット例:

```
step5: add CreateUserCommand tests
```

---

## Step 6: 一意制約の責任整理

### 目的

アリスアリス問題（同名ユーザー重複）の扱いを明確にする。

### 設計意図

* 同名ユーザーは禁止という「概念的ルール」はドメイン上のビジネス制約である
* ユースケース単位でその制約を明示的に表現する
* 並行実行時の最終的な物理保証はインフラ（DB一意制約）が担う

### 実装内容（現時点）

1. CreateUserCommand で事前重複チェックを実装
2. 重複時は IllegalStateException を送出する仕様にした
3. 正常系テストおよび重複時失敗テストを追加し、仕様を固定した

### トレードオフ

* Application層での重複チェックは並行実行では破れる可能性がある
* 物理保証をApplicationだけで完全に担うことはできない
* 本番環境ではDBの一意制約と組み合わせて初めて安全になる

コミット例:

```
step6-1: add duplicate check in CreateUserCommand
step6-2: add duplicate test case
step6-3: document uniqueness responsibility
```

# 最終目的

このプロジェクトのゴールは機能追加ではない。

最小ドメインで以下を体得すること：

* 依存方向を守る
* 責務を明確にする
* トランザクション境界を理解する
* 技術的保証と概念的ルールを分離する

ユーザー名しか持たない。
しかし設計密度は最大にする。

---

# 現時点での到達点（学習目標の完了）

本プロジェクトは、Clean Architectureにおける責任分離と依存方向の理解という学習目的を達成した。

* ドメインを中心とした依存構造を構築
* Repository抽象化とDIによる差し替え可能設計を実装
* ユースケース単位での責務分離を確認
* 一意制約の責任分担（概念・適用・物理保証）を整理
* テストにより仕様を固定

以上をもって、本プロジェクトは一旦「学習完了」とする。
